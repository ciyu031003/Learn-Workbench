## 一、P3 · 面试题库与模拟面试（主任务）

### P3-1 数据层（新增轻量表，建议一条迁移）
- [ ] 新增 `interview_attempts`（答题 / 面试记录）表：
  - `id / user_id`（**按账号隔离，必带**）/ `question_id`（引用 interview_questions，可空=自由模拟）/ `phase_id`（可选，关联路线图阶段）
  - `mode`（'quiz' 题库刷题 | 'mock' 模拟面试 | 'interview' 真实面试记录）/ `self_rating`（自评 1-5）/ `reaction`（答题用时）/ `chosen_answer`（用户作答）/ `is_correct`（对错，刷题时）/ `note`（复盘）/ `created_at`
  - 索引：(user_id)；沿用仓库 bigserial + user_id 隔离 + updated_at 约定
- [ ] schema.sql 全量对账 + 迁移文件（接 019 之后，如 `020_interview_attempts.sql`）
- [ ] 评审核对：**面试记录按 user_id 隔离**；interview_questions 是**共享题库**（非按用户）

### P3-2 题库 API + 刷题页
- [ ] `GET /api/questions`（题库列表 / 按 module 分组 / 难度筛选 / 分页）—— 共享题库，无需用户隔离
- [ ] `POST /api/questions/attempt`（提交一题作答 → 写 interview_attempts，返回对错 / 参考答案）
- [ ] `GET /api/questions/attempts`（我的答题历史 / 按 module 汇总 / 正确率）—— 按用户隔离
- [ ] 刷新 `/career/interview` 页为**可用页**：
  - 题库刷题卡片（module 分组 → 逐题作答 → 显示答案 → 标记掌握）
  - 答题统计（答题数 / 正确率 / 各 module 分布）
  - 与已完成的求职 Kanban 入口并列
- [ ] 复用仓库模式：每个 route.ts 配 route.test.ts；弹窗 / 筛选复用 GlassModal / FilterPanel 风格

### P3-3 面试记录 + 复盘（对应占位页第二点）
- [ ] 「面试记录」入口：一场面试绑定一个 job_application（见 P3-4）或纯记录
  - 面试类型/轮次（一面/二面/HR）、日期、自评、复盘结论、待改进点
- [ ] 复盘视图：按时间段 / 岗位汇总面试次数、通过率、常见丢分点

### P3-4 与求职 Kanban 联动（对应占位页第三点）
- [ ] 求职看板阶段 interview1 / interview2（已有）增加「记录面试」动作 → 新建该申请的面试记录
- [ ] 面试记录展示在对应申请卡片内（阶段流转时提示是否已记录）
- [ ] 联动：某岗位「加入求职」后，其面试记录累计到该申请；看板统计列「面试中 / 平均轮次」

### P3-5 面试维度接入职业准备度（替代 log_entries 近似）
- [ ] readiness.ts 面试维度改为读 interview_attempts（自评 + 次数），替代 log_entries(kind=interview) count×20
- [ ] 权重维持 15%（或可配置）；UI 文案从「N 篇面试日志」改为「刷题 N 题 · 面试 N 场」

### P3-6 验收
- [ ] 题库刷题 → 提交作答 → 看到对错/答案 → 生成记录 → 面试维度分数变化，全链路可跑
- [ ] 求职看板某申请可「记录面试」并回流展示
- [ ] web 单测 + E2E 补关键路径；pnpm test:e2e 通过；线上部署验证

## 三、边界与「不做」（控制范围）
- 面试题库是**共享数据**（非按用户），不引入用户自定义题库（除非后续明确要）；答题记录才按用户隔离。
- 面试维度初始不建缓存结果表，实时聚合足够；数据量大后再上 `career_readiness` 缓存表（路线图已作备选）。
- 模拟面试的 **AI 部分后置到 P5/P6**，先跑通规则化闭环，避免一上来依赖 AI。
