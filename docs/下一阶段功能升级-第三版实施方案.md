# Learn-Workbench 下一阶段功能升级实施方案 V3.0

> **版本**：V3.0（第三版）
> **定位**：在 V2.0 蓝图之上，先对齐「当前仓库真实状态」，再收敛为可落地、增量、可回滚的实现方案。
> **版本关系**：V1（从零扩功能）→ V2（开源参考 + 领域化 + UI 规范）→ **V3（删去已落地项、补齐真缺口、给每一 Phase 明确验收口径）**。
> **核心原则（继承 V2，绝不放松）**
> 1. 不推倒现有 Monorepo / PostgreSQL / shared / 招花采集 / Focus / 同步。
> 2. 不把开源项目直接拼进来（Resume←Reactive Resume、Fitness←wger、Career←JobSync、Habit←BeHabit 仅作领域参考）。
> 3. UI 严格继承 Liquid Glass + 每日 Bing 风景背景，**主品牌色唯一，语义色只表状态**。
> 4. 不一次性建空 API / 空表 —— 按 Phase 增量交付，每 Phase 独立可验证、可回滚。

# 1. V3 裁剪原则（相对 V2 的关键变化）

V2 的问题不是方向错，而是**把「已做完」也排进了 Phase**，且缺少「怎么验收/怎么回滚」的口径。V3 做三件事：

1. **S（Skip）**：V2 Phase 2/4/6/7（Certificate、Career Radar、Application、Employment Market）**不是删除规划**，而是把「已落地部分」标记为 ✅，V3 只做其中**未闭环**的增量。
2. **P（Prioritize）**：按「对现状增益最大 + 复用现有资产最多」重排 Phase（见 §5 路线图）。
3. **A（Acceptance）**：给每个 Phase 加**明确完成口径**与**回滚点**（迁移可降级、开关可关、旧 UI 保留）。

**V3 不做的（明确写死，防止范围蔓延）**
- ❌ 重做招花采集、市场工作台、领域化、任务/日志/专注/同步、求职/面试（已稳定）。
- ❌ 一次性把五大 Domain 全抽象出来（会大动现有表，风险高、与「只追加迁移」冲突）。
- ❌ 引入陈旧的大型第三方域（wger 的 AGPL 代码不直接并入；Resume PDF 优先用现有轻量方案/含许可的渲染库）。
- ❌ 新增的第二套 Glass Card / 第二套计时器 / 第二套主题色。

V2 提出 Profile/Learning/Career/Fitness/Daily 五个 Domain。V3 承认这个概念架构，但**本期只把真正缺少的落库，其余停留在「API/页面归属」层面**，不做强行表重构：

```text

Learning ← 已落地（领域化 024–028），本期不动

Fitness  ← 本期重点：Workout Plan/Exercise/Set + Nutrition + (Habit 并入)
Daily    ← 本期收尾：把 Learning/Career/Fitness/Habit 当日数据聚合为「我的一天」
```

# 5. V3 推荐实施路线图（重排后）

> **Phase 顺序（已按本次决策定稿）**：Profile 收敛 → **专注计时修正+正向** → Certificate → Resume(多模板/拖拽) → Career Radar(/api/jobs/radar B 为主) → Habit(独立表) → Fitness(A 轻量)+Nutrition → Daily → Sports。
> 相对 V2 加严两点：**专注计时修正/正向计时为高优先 P0**（复用最多、解决真实痛点）；**Radar 走 B 为主 + A 兜底的批量匹配**，避免逐岗位并发压力。

```text
Phase 0  现状审计（本节即审计；落地前跑 pnpm -F web test/lint/typecheck 建立基线）
   │
Phase 1  Profile 信息源收敛 + Design Token 一致性微调（不换主题）
   │
Phase 2  专注计时修正（后台/前台墙钟对时）+ 正向计时（秒表）模式   ← 高优先，复用最多
   │
Phase 3  Certificate 独立领域（迁移 036+）
   │
Phase 4  Resume Engine v1（多模板 + A4 预览 + 拖拽 + 导出）
   │
Phase 5  Career Radar 聚合视图 + /api/jobs/radar 批量匹配（B 为主）(缺画像回落 A)
   │
Phase 6  Habit（迁移：独立 habits/habit_logs 表）──────┐
   │                                                  │
Phase 7  Fitness Plan（轻量 A）+ Nutrition            ├─ 并入 Daily/分享
   │                                                  │
Phase 8  Daily OS 聚合页  ────────────────────────────┘
   │
Phase 9  Sports Profile / Share
   │
Phase 10 收尾回看（Mobile 对齐、可访问性、License 记录、回归）
```

> **每 Phase 的固定模板**（写入 codex 提示词）：
> ① 先读现状（CLAUDE.md + 看板 + 目标文件）；② 只追加迁移，新表同步进 `schema.sql`；③ 数据按 `user_id` 隔离；④ API 必带 `route.test.ts`；⑤ 复用 `packages/ui` 与 glass token，禁新建第二套 Card；⑥ 移动端走 `makeStyles(colors)` + ThemedIcon；⑦ 跑 `pnpm lint/typecheck/test/build`，涉 E2E 跑 `pnpm test:e2e`；⑧ 记录到 `改动记录与任务看板.md`。

# 7. UI 视觉总纲（继承 V2，声明为硬约束）

- **绝对唯一主品牌色**：新增模块绝不各自定义主题色；只允许极轻微语义色（success/warning/danger/info）表达状态。
- **Glass 规则**：玻璃表面 + blur 24px + saturate 1.8 + 渐变高光边缘 + 动态文字对比；禁止大面积纯白卡/实心按钮/传统后台表格叠玻璃。
- **Bing 背景**：保留每日风景背景；新页面上加 `Adaptive Overlay → Glass Surface → Content` 分层，保证数据可读。
- **Resume 例外**：**A4 简历本身不做玻璃**，必须专业克制、可打印（Glass Editor → Clean Professional Resume）。
- **Mobile ≠ 缩放 Web**：Mobile＝执行/记录/查看/分享，Web＝管理/分析/编辑；Resume 移动端＝编辑/预览切换，Kanban/Fitness 首页＝横滑或走子级页，避免 6+ Tab 拥挤（现 4 Tab + 子栈）。
- **代码复用优先**：所有新组件先进 `packages/ui` 或既有 UI 层，**不建第二套 Glass Card / 计时器 / 主题**。

# 10. 本版本最重要的结论

1. **先对齐现状，再谈开发** —— 仓库已比我预想更完整，V3 的价值在于「只补真缺口」，避免重复劳动。
2. **不推倒、不拼接、唯一视觉 DNA** —— 继承 V2 三大铁律。
3. **本期真正的前置工程是两件**：
   - **Profile 信息源收敛**（教育/经历/技能，一份数据喂 Resume/Treadiness），这是 Resume/Certificate/Career 的共同底座，必须先做。
   - **Resume Engine v1 + Career Radar**（P0）复用现有资产、增益最大。
4. **Habit / Fitness Plan / Nutrition / Sports / Daily** 作为 P1/P2 按独立迁移推进，各自可验收、可回滚。
5. **闭环仍然是最终目标**（目标→计划→行动→记录→数据→反馈→调整目标），但通过「聚合的 Daily OS + Public Share」收敛，不靠堆模块。

## 12-2 D4：「现有表能否直接升级对接 B（独立 habits 表）」

## 12-3 专注计时：后台/前台计时修正 + 正向计时（秒表）

### 现状核实（问题根因）
- **Web `components/focus-timer.tsx`**：计时用 `setInterval(1s)` 递减 `remaining`，**且累计只统计可见时间段**（`if (!document.hidden) visibleElapsedRef.current += 1`）。即切到别的标签/最小化会被设计性「暂停」，`pagehide`/`visibilitychange` 时结算。这是**有意为防刷**的取舍，但确实造成后台不计时。
- **Mobile `components/focus-timer.tsx`**：`setInterval(1s)` 直接递减 `remaining`；**iOS 后台会挂起 JS 定时器 → 倒计时在后台实际停止**，回前台时 `remaining` 没减，导致 `elapsed = total - remaining` **少算**后台时长。**无 `AppState` 监听做对时修正**。
- **前向（秒表/正向）计时模式：均不存在**。

### 目标改动（本期，Web + Mobile 都要）
1. **改为「墙钟对时」而非「interval 递减」**：维护 `startedAt`（wall-clock）+ 期望时长；每次 `tick/AppState 变化/回前台` 都用 `Date.now() - elapsed` 重算 elapsed/remaining，**后台计时不丢**。
2. **Web 后台策略与防刷**：Web 端是否「后台继续计时」需你确认一个口径（见下方**待你定夺**）。移动端直接用 `AppState` 事件在回前台时按 wall-clock 补计。
3. **新增「正向计时」模式**：专注计时器加「倒计时 / 正向（秒表）」两种模式；正向模式只累计跑了多久（可暂停/继续），结算同样写 `focus_sessions` / 运动记录。
4. 结算逻辑沿用：最短记录阈值（专注 5s / 运动 60s）、单会话上限 12h、client_id 幂等、15s 幂等 upsert — **不破坏**。

> **✅ 已确认（最终）**：Web 后台计时口径按 **A —— 后台继续计时**（与移动端一致，用 `pagehide` 校正；符合「后台/前台都要正常计时」诉求）。Web 端也改为墙钟对时 + 后台继续计时。
