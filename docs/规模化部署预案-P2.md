# 规模化部署预案（P2）——多用户扩展路径

> 状态：**预案**（当前单实例部署无需启用，按本文触发条件按需上线）。
> 关联：`docs/改动记录与任务看板.md`、`CLAUDE.md`。2026-09-06 P2 落地的代码部分：Redis 双后端限流/缓存（`lib/redis.ts` + `lib/rate-limit.ts` + `lib/daily-cache.ts`，`REDIS_URL` 未配置时自动走进程内）、匿名接口 nginx 缓存（`deploy/nginx/`）、登录异常量告警与慢查询日志。

## 1. 触发条件（什么时候需要动）

| 信号 | 观察方式 | 触发的动作 |
| --- | --- | --- |
| 单机 CPU/内存长期 >70%，或连接池频繁排队（日志 `connection timeout`） | `docker stats`、web 日志 | §3 多实例 + §2 Redis |
| 登录/受限接口限流在多实例下失效（每个实例各算各的） | 部署 ≥2 个 web 实例时必然出现 | §2 Redis（代码已就绪，只差 env） |
| 慢查询告警变频繁（`docker compose logs db` 里 `duration: xxx ms`） | PG `log_min_duration_statement=500`（compose 已配置） | §4 PgBouncer / 索引优化 |
| DB CPU 被 读请求 吃满 | `pg_stat_activity` / 云监控 | §5 读写分离（最后再考虑） |

## 2. Redis（限流/缓存多实例共享）——只差一个环境变量

代码路径已就绪：`REDIS_URL` 配置后，`rateLimit()` 与 AI tip 缓存自动切换到 Redis（Lua 原子固定窗口），Redis 故障自动降级进程内实现，不需要改任何业务代码。

```bash
# 服务器装 Redis（同机即可，仅内网监听）
sudo apt install redis-server
sudo systemctl enable --now redis-server
# .env 追加（compose web 服务会透传）
echo "REDIS_URL=redis://127.0.0.1:6379" >> .env
docker compose up -d web
```

验证：`docker compose exec web node -e "import('ioredis').then(({default:R})=>new R(process.env.REDIS_URL).ping().then(v=>{console.log(v);process.exit(0)}))"` 应输出 `PONG`。键前缀约定：`lwb:rl:*`（限流）、`lwb:cache:*`（缓存）。

注意：多实例部署前必须先上 Redis，否则限流窗口按实例各算各的（等于放宽 N 倍）。

## 3. 多实例（≥2 个 web 容器）

- 会话在 DB（token_hash），无本地会话状态 → **无需 sticky session**；
- 移动端/网页直接在前挂负载均衡（nginx upstream 或云 LB）；
- `task_runs` 表锁是 DB 级互斥，爬虫/聚合任务多实例下依然安全；
- 进程内 Map（`rate-limit`/`daily-cache` 降级路径、AI tip 缓存）在 Redis 模式下不再参与一致性，仅作故障兜底；
- 注意 `PGPOOL_MAX`（默认 20）× 实例数 + 聚合任务连接 ≤ `max_connections`（默认 100），不够就调 PG 或减池。

## 4. PgBouncer（连接数先爆时）

在 web 与 db 之间加 transaction 池，几十个应用连接复用几十个真实连接：

```yaml
# docker-compose.yml 追加
  pgbouncer:
    image: edoburu/pgbouncer:latest
    environment:
      DB_HOST: db
      DB_USER: lwb
      DB_PASSWORD: ${PG_PASSWORD}
      POOL_MODE: transaction
      MAX_CLIENT_CONN: 200
      DEFAULT_POOL_SIZE: 25
    depends_on: [db]
    networks: [lwb]
```

然后把 web 的 `PGHOST=pgbouncer`、`PGPORT=5432` 即可。**transaction 模式注意**：应用代码里所有事务都显式 `BEGIN…COMMIT`（已满足）；不要在事务外用 `SET`/prepared session 状态（`pg` 驱动的 prepared statement 需关闭：连接串加 `?prepared_statements=false` 或 PG16+ 默认兼容——上线前跑一遍全量测试确认）。

## 5. 读写分离（最后才考虑）

DB CPU 真正成为瓶颈再上：PG 流复制 1 从库 → 只读接口（market/公开统计/dashboard 查询）走从库连接串 `PGRO_HOST`（需要代码层读写分离路由，当前未实现，先别上）。**优先级永远低于：加缓存（已做）→ 索引优化 → PgBouncer → 多实例。**

## 6. 监控告警（已落地部分）

- **慢查询**：compose db 服务已带 `log_min_duration_statement=500`，`docker compose logs db | grep duration` 查看；接日志采集（如腾讯云 CLS）可配告警。
- **登录异常**：每日 06:10 maintenance job 扫 `auth_attempts`，24h 失败 ≥200 次或单账号 ≥30 次 → web 日志输出 `[security] 异常登录失败量…`；`cron-jobs.log` / `docker compose logs web` 可采集告警。阈值可用代码内 `securityAlerts({maxFailures24h, maxPerUsername24h})` 调整。
- **缓存命中**：nginx 缓存启用后 `access_log` 的 `$upstream_cache_status`（HIT/MISS）可统计匿名接口命中率。
