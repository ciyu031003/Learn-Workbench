# ADR 纪律与序列

架构决策记录（Architecture Decision Record）：把"当时为什么这么选"钉在仓库里，
免得半年后有人（包括未来的自己）把已被否决的方案再提一遍。

## 1. 什么时候必须写 ADR

满足任一条就要写，**先写 ADR 再动手**：

- 引入/替换一个外部依赖或服务（Redis、CDN、队列、第三方 SDK）；
- 改变数据模型（新表、改语义、改 ID 规则）；
- 改变接口契约或对外行为（版本策略、错误结构、分页约定）；
- 做出"不做什么"的决定，且这个决定容易被后来者当成遗漏（例如"三域不合并，只建桥"）；
- 任何会写入"验收标准/回滚方式"的改动。

不必写 ADR 的：纯实现细节、样式调整、测试补充、依赖小版本升级。

## 2. 编号与状态

- 文件：`ADR-NNN-短标题.md`（三位数字，从 001 开始，**不复用、不重排**；废止的也不删）。
- 状态机：`提议` → `已采纳` → （必要时）`已被 ADR-NNN 取代` / `已废止`。
  改变决定时**新写一份**并回链旧的那份，不修改原文（历史要留痕）。
- 模板：`_template.md`。

## 3. 每份 ADR 必须有的字段

`状态` / `日期` / `阶段` / `相关文件` / `背景（真实代码或实测依据）` / `决策` / `备选方案与为什么不选` /
`影响与验收` / `后续（未闭合项）`。

其中两条最容易漏，必须写实：

- **背景**必须是可核对的依据（文件路径、迁移号、查询结果），不能是"感觉应该"；
- **备选方案**至少要有一个真被考虑过的，并写清否决理由。

## 5. 与阶段汇报的关系

每个阶段的汇报（`../reports/`）必须给出「发现 / 改动 / 验证 / 风险 / 下阶段」，
并在开头列出本阶段涉及的 ADR 编号（没有就写"无"，不要省略这一行）。
